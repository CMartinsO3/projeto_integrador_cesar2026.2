Desafio de Engenharia

O problema que precisávamos resolver

O HemoFlow gerencia a alocação crítica de hemocomponentes (ABO/Rh + FEFO) e roteamento de cadeia fria entre o HEMOPE e 11 hospitais de Recife. A infraestrutura precisava garantir integridade e prontidão imediatas.

Sem Docker: O Labirinto do Ambiente

Gargalos Reais
✕

Drift de Versões & "Na minha máquina funciona"

Divergência entre JDKs instalados (Java 17 Temurin vs OpenJDK genérico), versões de Maven e variáveis de ambiente em Windows, macOS e Linux.

✕

Dependência Externa de PostgreSQL

Obrigatoriedade de cada desenvolvedor instalar e configurar o PostgreSQL 16 manualmente com usuário hemoflow, porta 5432 e banco local.

✕

Race Condition na Inicialização

O Spring Boot iniciava antes do PostgreSQL aceitar conexões TCP, resultando em falhas de conexão imediatas (Connection Refused) na subida.

✕

Risco de Poluição e Perda de Estado

Falta de separação limpa entre dados sintéticos de teste e banco de desenvolvimento, com difícil replicação no pipeline de CI/CD.

Com Docker: O Ambiente Blindado

Implementado
✓

Multi-Stage Build Padronizado

O build ocorre dentro de maven:3.9.9-eclipse-temurin-17 com dependências em cache e geração de runtime leve em eclipse-temurin:17-jre-jammy.

✓

Orquestração com compose.yaml

Um único comando levanta a API Java e o container postgres:16.4-alpine, isolando a porta 5432 dentro da rede interna.

✓

Coordenação por Healthcheck (Zero Race Condition)

Uso de depends_on.db.condition: service_healthy. A API aguarda o PostgreSQL responder ao pg_isready antes de iniciar.

✓

Persistência Controlada via Volume Nomeado

Volume hemoflow_pgdata preserva o estado entre reinicializações e permite descarte limpo através de docker compose down -v.

Papel na Arquitetura

Hospeda a API Spring Boot do HemoFlow. Executa o algoritmo de caminhos mínimos (Dijkstra) para a logística da cadeia fria e alocação de hemocomponentes por FEFO e compatibilidade ABO/Rh.

Configuração em compose.yaml 
api:
  build:
    context: .
    dockerfile: Dockerfile
    args:
      GIT_SHA: ${GIT_SHA:-local-compose}
      APP_VERSION: ${APP_VERSION:-0.0.1-SNAPSHOT}
  container_name: hemoflow-api
  restart: unless-stopped
  depends_on:
    db:
      condition: service_healthy
  ports:
    - "${PORT:-8080}:${PORT:-8080}"
  environment:
    SPRING_PROFILES_ACTIVE: ${SPRING_PROFILES_ACTIVE:-postgres}
    SPRING_DATASOURCE_URL: jdbc:postgresql://db:5432/hemoflow
  healthcheck:
    test: ["CMD-SHELL", "curl -fsS http://localhost:$${PORT:-8080}/actuator/health || exit 1"]
    interval: 15s
    timeout: 5s
    retries: 5
    start_period: 40s
Benefício de Engenharia

A API nunca tenta conectar no banco prematuramente devido à condição service_healthy, garantindo inicialização limpa e determinística.

Construção da Imagem

Por dentro do Dockerfile

Análise do Dockerfile autêntico do HemoFlow: padrão Multi-Stage Build, otimização de cache de dependências e segurança com usuário não-root.

Dockerfile (37 linhas)
1 FROM maven:3.9.9-eclipse-temurin-17 AS build
2 WORKDIR /app
4 COPY pom.xml mvnw ./
5 COPY .mvn .mvn
6 RUN chmod +x mvnw && ./mvnw -B dependency:go-offline
8 COPY src src
9 RUN ./mvnw -B verify
11 FROM eclipse-temurin:17-jre-jammy AS runtime
17 LABEL org.opencontainers.image.title="HemoFlow API"
26 RUN groupadd --system --gid 1001 hemoflow && useradd --system --uid 1001 --gid hemoflow --shell /sbin/nologin hemoflow
29 COPY --from=build --chown=hemoflow:hemoflow /app/target/*.jar /app/app.jar
31 USER hemoflow
32 EXPOSE 8080
34 HEALTHCHECK --interval=15s --timeout=5s --start-period=40s --retries=5 CMD curl -fsS http://localhost:${PORT}/actuator/health || exit 1
37 ENTRYPOINT ["java", "-jar", "/app/app.jar"]
Estágio 1 • Linhas 4-6 Cache Otimizado de Dependências Maven
O arquivo pom.xml e a pasta .mvn são copiados antes do código-fonte. O comando ./mvnw -B dependency:go-offline baixa todas as dependências em uma camada isolada de cache.
Por que no HemoFlow: Alterações no código em src/ não forçam o re-download de ~200MB de bibliotecas Maven a cada novo build.
Estágio 1 • Linha 9 Gate de Testes no Próprio Build
O comando ./mvnw -B verify compila e executa toda a suíte de testes (39 testes unitários, integração e cenários BDD Cucumber). Se qualquer teste falhar, a imagem sequer é gerada.
Por que no HemoFlow: Garante que nenhuma imagem com regras de compatibilidade ABO/Rh ou FEFO quebradas seja empacotada.
Estágio 2 • Linhas 26-31 Segurança: Princípio do Menor Privilégio
Criação de usuário dedicado de sistema hemoflow (UID 1001, GID 1001) com shell restrita /sbin/nologin. O artefato compilado é copiado com --chown=hemoflow:hemoflow e executado sob USER hemoflow.
Por que no HemoFlow: Elimina o risco de execução como root, protegendo o sistema host contra eventuais brechas de segurança no container.
Orquestração Declarativa

Docker Compose: stack coordenada

Como o compose.yaml coordena dependências, redes, persistência e saúde dos serviços em um único manifesto declarativo reproduzível.

1. Dependência Condicional (service_healthy)

depends_on

O Compose aguarda o PostgreSQL passar no teste de saúde (pg_isready) antes de disparar o container da API. Evita o erro clássico de Connection Refused durante o boot do Spring.

depends_on: db: condition: service_healthy

2. DNS Embutido & Rede Bridge Isolada

hemoflow-net

A API se conecta via JDBC usando o hostname db (resolvido automaticamente pelo Docker). A porta 5432 do banco não fica exposta no host, reduzindo a superfície de ataque.

SPRING_DATASOURCE_URL: jdbc:postgresql://db:5432/hemoflow networks: - hemoflow-net

3. Persistência de Volume (hemoflow_pgdata)

Named Volume

Os dados sintéticos de hospitais, bolsas de sangue e requisições são preservados após docker compose down. O reset intencional só ocorre se o usuário passar a flag -v.

volumes: hemoflow_pgdata: name: hemoflow_pgdata
compose.yaml (Visão Sintética Integral) Docker Compose v2
services: db: image: postgres:16.4-alpine container_name: hemoflow-db restart: unless-stopped environment: POSTGRES_DB: ${POSTGRES_DB:-hemoflow} POSTGRES_USER: ${POSTGRES_USER:-hemoflow} POSTGRES_PASSWORD: ${POSTGRES_PASSWORD:-hemoflow_local_dev} volumes: - hemoflow_pgdata:/var/lib/postgresql/data networks: - hemoflow-net healthcheck: test: ["CMD-SHELL", "pg_isready -U $${POSTGRES_USER} -d $${POSTGRES_DB}"] interval: 10s retries: 5 api: build: context: . dockerfile: Dockerfile container_name: hemoflow-api depends_on: db: condition: service_healthy ports: - "${PORT:-8080}:${PORT:-8080}" environment: SPRING_PROFILES_ACTIVE: postgres SPRING_DATASOURCE_URL: jdbc:postgresql://db:5432/hemoflow healthcheck: test: ["CMD-SHELL", "curl -fsS http://localhost:$${PORT:-8080}/actuator/health || exit 1"] volumes: hemoflow_pgdata: networks: hemoflow-net: driver: bridge

Guia Operacional

Como executar o projeto

Comandos autênticos para compilar, executar, inspecionar e encerrar o ambiente. Clique no ícone de cópia para transferir o comando para sua área de transferência.

Build & Execução Primeiro Boot
Subir a stack completa com rebuild

Compila a imagem multi-stage validando todos os 39 testes e inicializa o PostgreSQL e a API em foreground.

docker compose up --build
Background Modo Detached
Subir ambiente em segundo plano

Libera o terminal imediatamente, mantendo os containers em execução contínua com política unless-stopped.

docker compose up -d
Diagnóstico Status & Health
Verificar integridade dos containers

Exibe o estado de saúde reportado pelos healthchecks (healthy) de hemoflow-api e hemoflow-db.

docker compose ps
Observabilidade Streaming Logs
Acompanhar logs da API HemoFlow

Monitore em tempo real as operações de alocação de sangue (FEFO), cálculo de Dijkstra e logs do Spring Boot.

docker compose logs -f api
Smoke Test Validação HTTP
Validar endpoint de saúde (Actuator)

Confirma se a API está online e se a conectividade com o banco PostgreSQL está saudável (retorna status: UP).

curl -fsS http://localhost:8080/actuator/health
Encerramento Preserva Dados
Parar stack mantendo o banco de dados

Para e remove os containers e redes, preservando os estoques e topologias salvos no volume hemoflow_pgdata.

docker compose down
Impacto no Projeto

O que ganhamos com Docker

Conexão direta entre as tecnologias implementadas e os ganhos práticos comprovados no HemoFlow, diferenciando o que foi entregue das evoluções futuras.

Paridade Absoluta Dev / CI / Prod

O mesmo Dockerfile e compose.yaml são executados localmente e no GitHub Actions (job compose-smoke), eliminando divergências de sistema operacional.

✓ Evidência: .github/workflows/ci.yml

Segurança com Usuário Não-Root

O container de runtime é executado sob o usuário hemoflow (UID 1001, GID 1001), garantindo conformidade com o princípio de menor privilégio na execução.

✓ Evidência: Dockerfile (linhas 26-31)

Orquestração por Prontidão Real

A eliminação de race conditions através de service_healthy garante que a aplicação Spring Boot só inicialize após o PostgreSQL estar apto a aceitar queries.

✓ Evidência: docs/evidencias/e1/compose-ps.txt

Isolamento e Persistência Determinística

Nenhum desenvolvedor precisa instalar ou poluir seu host com instâncias PostgreSQL. O ciclo de vida dos dados é controlado perfeitamente via volumes nomeados.

✓ Evidência: persistencia-volume.txt
Diferenciação Rigorosa de Escopo
Efetivamente Implementado

Containerização multi-stage, compose local com PostgreSQL 16.4 Alpine, validação automatizada de compose em CI (Ubuntu 24.04), smoke test HTTP contra endpoints reais e build com gate de 39 testes.

Evolução Futura / Potencial

Clusterização com Kubernetes (K8s), autoscaling horizontal de pods da API, replicação primário-réplica de banco de dados e balanceamento de carga com Nginx/Traefik.
