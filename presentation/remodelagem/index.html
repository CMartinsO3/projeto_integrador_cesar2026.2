Hoje: Spring Boot 3 + Thymeleaf + REST /api/v1, um PostgreSQL para tudo. ABO/Rh, FEFO, Dijkstra e cadeia fria já funcionam. Pipeline Docker → GHCR → Render com gate de testes.

Problemas (um por clique):

  • “Hospital” significa duas coisas: quem pede e o nó do grafo.
  • Regras espalhadas — controller falando direto com repositório.
  • Telemetria tem volume muito maior que cadastro: escala desigual.
  • Todo módulo lê toda tabela: dados acoplados.

22 termos no documento · seção 2.3

“Hospital” virou dois conceitos: Solicitante (Requisições) e Nó (Logística).

  • Alocação: decisão de quais bolsas atendem a requisição (proposta → confirmada).
  • Reserva: bloqueio temporário no Estoque; expira se não confirmada.
  • FEFO: First Expired, First Out.
  • Limite de cadeia fria: 120 min hemácias, 90 min plaquetas.
  • Guia de transporte: bolsas em FEFO, rota, temperatura, checklist, assinaturas.
  • Estoque insuficiente: sem bolsas compatíveis e válidas → aguardando estoque.
DDD estratégico · mapa de contextos

Quem depende de quem

Seta = upstream → downstream.

  • Clique 1 — o que chega na Alocação: Captação → Estoque (Customer-Supplier, evento DoacaoRegistrada); Requisições → Alocação (Published Language, RequisicaoAberta); Estoque → Alocação (Open Host Service: API de reserva de bolsas).
  • Clique 2 — o que sai: Alocação → Logística (Customer-Supplier, AlocacaoConfirmada); Indicadores é Conformist (read model dos eventos).
  • Clique 3 — telemetria: Telemetria → Logística (LeituraRegistrada); Sensores entram por uma ACL que traduz o pacote do sensor.
  • Identidade: OHS + Conformist — token JWT usado por todos.

Raiz Alocacao: id, requisicao (RequisicaoRef), itens (ItemAlocado 1..*), status. VOs: RequisicaoRef, JanelaEntrega, Quantidade, TipoSanguineo, Hemocomponente, Validade.

Domain services: PoliticaCompatibilidadeAboRh (matriz 8×8, O(1)) e SelecionadorFEFO. Repositório AlocacaoRepository. EstoquePort é a ACL que traduz Bolsa → BolsaCandidata. AlocarRequisicaoHandler orquestra: carrega → propõe → reserva → confirma.

Invariantes (um por clique): compatível; válida até a janela; FEFO com desempate por id; soma = quantidade; uma alocação ativa (confirmada não volta a proposta); mesmo hemocomponente.

Nenhum serviço lê o banco do outro.

  • Clientes (web, hospitais via REST, app do motorista) → API Gateway: roteamento, JWT, rate limit, CORS.
  • Clique 1: banco por serviço — PostgreSQL por contexto; telemetria em séries temporais.
  • Clique 2: barramento de eventos (RabbitMQ ou SNS+SQS).
  • Clique 3: serverless opcional — fn-guia-transporte já roda em Cloudflare Workers; fn-notificacoes por evento.
  • Clique 4: integração só por API ou evento.

Plataforma transversal: segredos em cofre, TLS, JWT validado no gateway; retry + DLQ, outbox, idempotência; GitHub Actions → GHCR/ECR → deploy por serviço; logs centralizados, métricas, OpenTelemetry, /actuator/health.

A guia de transporte já roda serverless: o 1º pedaço da fase 2 está pronto.

  • Fase 1 (~3 semanas): pacotes por contexto, três camadas, eventos internos + outbox, um schema por contexto, testes ArchUnit. = Cenário A.
  • Fase 2 (~3 meses): gateway na frente; saem svc-logistica (core) e svc-telemetria (volume); broker gerenciado; funções serverless. = Cenário B (alvo).
  • Fase 3 (sob gatilho): demais contextos + infra como código, só se: >50 hospitais, >1 milhão de leituras/dia, SLA 99,9% ou >3 squads. = Cenário C.
